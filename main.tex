        Visiualization library archictecture determines the technical limits of how accessible a library can be. The accessibility of visualizations and visualization tools is highly determined by the tools they are built with and it is the architecture of these upstream tools that determines what accessibility is feasible to implement. Matplotlib is a building block \cite{wongsuphasawatNavigatingWideWorld2021}
Python library that developers can use to build static, animated, and interactive visualizations. Matplotlib's API aims to facilitate option driven design \cite{elavskyOptionDrivenDesignContext2023} by providing defaults that are accessible under many criteria and options for almost every visual element it generates. This customizability is possible because of modular Matplotlib's architecture; every visual element in an image produced by Matplotlib -  every line, text, image - is backed by an object called an Artist \cite{hunterArchitectureOpenSource}. Generally, the encoding/(aesthetic) information is passed into the artist, rather than part of its implementation, which is why Artists can be customized to be accessible. Each artist knows the properties of the element it is abstracting and if it is the child of another artist, such as if it is a line inside a figure. This information could be exposed to accessibility tools, such as alt-text generators or image navigators, through an API and the Matplotlib developers invite feedback on what information would be useful to expose.


\section{Visual Variables: Color and Texture}

Matplotlib allows users to customize aesthetics to fit many accessibility needs and sets accessible default colormaps, sequences, and texture patterns to aide users who do not have expertise in building accessible visualizations. Matplotlib also provides a method for creating reusable stylesheets \cite{CustomizingMatplotlibStyle}, which allow the users to set default values for many of the aesthetic parameters of specific artists, e.g. "lines.linewidth : 3" and "xtick.labelsize : 16". These stylesheets are composable; for example, users can compose a stylesheet setting accessible colors with a stylesheet that adjusts text sizes and line widths for posters. 

\subsection{Color}
\begin{figure}
        \centering
        \includegraphics[width=\linewidth, alt={Visual listing of the colors in the Okabe Ito, Petroff 6, 8, and 10, and Tableau 10, 20, 20b, and 20c named color sequences}]{color_sequences.png
        }
        \caption{Matplotlib provides the Okabe-Ito, four Tableau, and three Petroff accessible color sequences. Each sequence is designed so that each color is perceptually distinguishable from the other colors in the sequence.}
        \label{fig:color_cycle}
\end{figure}

Matplotlib's color sequences (palettes) are used by the plotting methods to automatically assign colors to visual elements. When plotting multiple line plots, for example, the first line takes the first color of the sequence, the second line takes the second color, the nth line the nth color, and the sequence cycles once the colors are exhausted. As shown in \autoref{fig:color_cycle}, Matplotlib's default color sequence is the tableau color sequence, which is designed to be accessible to people with color vision deficiencies (CVD) \cite{stoneHowWeDesigned}. The Petroff color sequences \cite{petroffAccessibleColorSequences2024} were added in versions 3.10.0 and 3.11.0 and are designed with the aide of machine learning to balance accessibility constraints with aesthetic considerations. The Okabe-Ito sequence was added in 3.11.0 and aims to have reliable contrast on light and dark backgrounds and when converted to CYMK for printing\cite{ichiharaColorUniversalDesignThe2008}. 

\begin{figure}
        \centering
        \includegraphics[width=\linewidth, alt={The berlin colormap goes dark blue to reddish pink, the managua colormap goes sky blue to orange, and the
        vanimo colormap goes bright green to bright pink. All three colormaps have a black center.}]{darkcmap.png}
        \caption{The berling, managua, and venimo are dark-mode diverging colormaps,
        with minimum lightness at the center, and maximum lightness at the extremes.}
        \label{fig:dark_color_map}
\end{figure}

All of Matplotlib's sequential and diverging colormaps are perceptually uniform and the default colormap `Viridis' is designed to be distinguishable for people with most forms of CVD \cite{enthoughtBetterDefaultColormap2015}. Additionally, the diverging dark mode colormaps \cite{crameriScientificColourMaps2023} in \autoref{fig:dark_color_map} were added in version 3.10.0 to support dark mode displays. If these color sequences or maps do not suit the situation, Matplotlib also allows users to customize the color of every visual element in an image through the Artist interface. The colors can be specified in RGB/RGBA, HEX, grayscale, x11/CSS4, and a few library specific formats\cite{SpecifyingColorsMatplotlib}. The colors module supports creating custom linear and categorical colormaps, the normalization module provides a variety of methods for encoding numbers as colors, the new colorizer module allows for even more customizability. Users can also create custom colormaps and norms and register external libraries of colormaps.

\subsection{Texture}

In addition to or in place of color, Matplotlib has rich support for using textures to add visual distinguishability in a graphic Matplotlib supports almost 40
named marker styles, markers created from Tex symbols, and custom markers created from
paths (arbitrary shapes) \cite{MarkerReferenceMatplotlib}. Additionally, Matplotlib
provides 4 named line styles ('solid', 'dotted', 'dashed', 'dashdot') and allows users
to configure the on/off sequence to create arbitrary patterns. Matplotlib also supports
10 hatch patterns (\texttt{/|-+*.xoO}) that, as shown in \autoref{fig:hatch_patterns}, can be combined and can also be made more dense by repeating the specification,
i.e. 'oo' yields more closely spaced circles. Additionally, Matplotlib supports generating custom fill patterns, as exemplified by third party libraries such as
\cite{leeMpl_pe_pattern_monster011Documentation}.

\section{Text}
As with color and texture, Matplotlib's fonts allow a very high level of customization so that users can choose the fonts, styles, weights, sizes, and colors best suited for their audience\cite{FontsMatplotlibMatplotlib}. In addition, Matplotlib also has a robust API for formatting ticks \cite{MatplotlibtickerMatplotlib3103}. The default font \texttt{DejaVu sans}\cite{DejaVuFonts} provides characters that are sans serif, unembellished, and distinguishable but does not guarantee consistent stroke width or symbol spacing. 
\begin{figure}[!h]
        \centering
        \includegraphics[width=\linewidth, alt={}]{libraqm.png}
        \caption{}
        \label{fig:libraqm}
\end{figure}

Version 3.11 improves support for non-Latin alphabets; this can improve accessibility because graphs can be more easily created and understood when they incorporate conventions from the user's socio-cultural experiences \cite{byrneAcquiredCodesMeaning2016}. This support is being added through the adoption of \texttt{libraqm} \cite{HOSTOmanLibraqm2025} as the text engine. As shown in \autoref{fig:libraqm}, \texttt{libraqm} supports right-to-left and left-to-right texts, and  parsing and placing letters, vowels, diacritics, and variant character forms correctly\cite{WhatHarfBuzzHarfBuzz,WhyNeedShaping}; therefore migrating to \texttt{libraqm} allows Matplotlib to more easily support most of the writing systems covered by the Unicode standard.

\section{Alt text \& Aria}

Matplotlib's goal of being backend independent drove an architecture decision to separate the artists from the backends\cite{BackendsMatplotlib3110}, which are (very loosely) the software that displays the visual element specified by the artist. Broadly, backends include static rendering engines such as Agg, Cairo, and PDF and interactive GUI frameworks such as QTAgg, GTKCairo, and ipympl. This separation of concerns at the architecture layer makes it technically feasible to develop accessibility API drawing from the Artist and customized to each backend, but the lack of consistent standards for wgar information should be passed along, and how, makes it unclear what that API should be. 

\subsection{Static Backends}

Matplotlib can write arbitrary metadata, including EXIF tags to the static image files, (e.g. png, jpeg, pdf, gif) it can output, which developers can use to build downstream tools targeted to specific backends, such as MatplotAlt\cite{nylundMatplotAltPythonLibrary2025} for computational notebooks, or custom accessibility aware backend layers such as py-maidr\cite{PymaidrAccessibleData}. Matplotlib could encourage this adaptor like approach, similar to Olli\cite{blancoOlliExtensibleVisualization}, but it raises questions on which defaults and guardrails, as described in the Bokeh Accessibility Audit \cite{elavskyBokehAccessibilityAudit}, Matplotlib should implement internally vs delegate to downstream libraries implemented by developers who have expertise in accessibility. For example, some formats (e.g. vector) have the ability to attach information to individual parts of a figure, whereas raster formats can only attach such alt text to the figure as a whole. Matplotlib can attach this information at the figure level and the artist level, but would it be more useful for Matplotlib to pass the tree to downstream tools or combine the information depending on backend? Should Matplotlib auto populate fields using artist information or raise a warning that users did not add alt text or neither? It is these trade offs between defaults and flexibility that Matplotlib developers would appreciate guidance. 

\subsection{Interactive Backends}
Matplotlib's backend independent widget system is implemented by rendering most of the Matplotlib interactive backends as static PNGs with an event system layer on top. This means that a lot of accessibility tools, such as key bindings, are implemented in the respective GUI framework rather than Matplotlib, and that screen readers cannot query the individual elements. The advantage of this approach is that developers are not limited to the widgets provided by a specific framework and instead can build basically any interaction that the event system\cite{InteractiveFiguresAsynchronous} supports, which itself is another form of supporting full customization to create interfaces tailored to a specific audiences access needs. The limited accessibility could potentially be addressed through the implementation of layers, for example something like the semantic layers in \cite{plotnine} specifically targeted to screen readers, as recommended by WebAIM\cite{WebAIMCSSAction}. Like the static APIs, the technical feasibility of this approach is due to the design decisions made to facilitate multiple backends. 


\section{API for accessibility tools}

There has been ongoing work to implement a new data container in Matplotlib to provide a uniform interface to the data. This interface unifies the model of internal state and provides a consistent interface for accessibility tools to query for information about the state of the visualization. A secondary goal of this work was reworking the visual encoding and assembly work handled by the artist into a more modular pipeline that is also more explicit about how visual elements correspond to distinct data elements. Maintaining that correspondance would allow the artist to retain more information about the visual elements and this information could be passed along to screen readers in a reliable way. The new transformation pipeline is also intended to keep track of the underlying structure of the data, providing a framework for developers to safely stack composable encoders (akin to the Encodable library \cite{wongsuphasawatEncodableConfigurableGrammar2020}). For example, a method for converting an arbitrary colormap to a cvd safe one can be verified to be structure compatible if it knows the structure of the data it is converting. The same is true for the full visualization, for example a structure aware pie chart can more reliably swap in accessible elements for accessible elements, such as replacing colors with hatches. To implement structure awareness, work needs to be done towards standardizing the properties of the internal visual parameters of Matplotlib. Like standardizing the data interface, standardizing the parameters would improve accessibility by creating a consistent standard for developers writing new functionality, such as libraries for accessible stylesheets or auto generating alt text, to hook into. 


\section{Conclusion}
Matplotlib's option driven design provides accessible defaults and many ways to customize the graphic to make the various elements more accessible. There are architectural challenges that make it difficult to make interactive visualizations accessible, but the artist tree stores information that could potentially be exposed to accessibility tools to compensate for the inability to introspect GUI elements. It is unclear how much of this information would be useful to expose, nor in what manner, and input from the accessibility researcher community would be very welcome.
