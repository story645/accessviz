%% Abstract section.
\abstract{Matplotlib was designed with the option driven design (ODD) goal of 
providing a high degree of customization and defaults that are appropriate for many different use cases. To achieve a balance of configurability and maintainability, Matplotlib has a modular architecture where visual information is encapsulated in the artist objects and output is managed by independent backends. This architecture makes it feasible to implement more accessibile options in the library and expose more information about the visualization to downstream accessibility tools, but the Matplotlib maintainers lack the expertise in accessibility to gauge what would be useful to implement internally and what information would be useful to expose through a public API. 
} % end of abstract

Matplotlib is a building block~\cite{wongsuphasawatNavigatingWideWorld2021}
Python library that developers can use to build static, animated, and interactive visualizations. Matplotlib's motto is "make simple things easy and difficult things possible", which is essentially option driven design (ODD), which is a practice of building systems that users can configure to their needs~\cite{elavskyOptionDrivenDesignContext2023}. Matplotlib tries to achieve this goal by providing options for almost every visual element it generates. Since not every user needs or wants this level of personalization, Matplotlib also provides defaults that users can hopefully use in many situations. This customizability is possible because of modular Matplotlib's architecture; every visual element (e.g. line, text, image) in a visualization produced by Matplotlib is backed by an object called an Artist ~\cite{hunterArchitectureOpenSource}. Generally, the encoding/(aesthetic) information is passed into the artist, rather than part of its implementation, which is why Artists can be customized to be accessible. Each artist knows the properties of the element it is abstracting and if it is the child of another artist, such as if it is a line inside a figure. This information could be exposed to accessibility tools, such as alt-text generators or image navigators, and the Matplotlib maintainers invite feedback on what information would be useful to expose through a public API.

In this paper, we document the options in Matplotlib that enable building accessible visualizations, the ongoing work of adding more accessible options, the limitations of the current implementation, and how Matplotlib's option driven design enables potentially building interfaces, libraries and tools to improve accessibility,

\section{Visual Variables: Color, Texture, and Shape}

Matplotlib allows users to customize aesthetics to fit many accessibility needs and sets accessible default colormaps, sequences, and texture patterns to aid users who do not have expertise in building accessible visualizations. Matplotlib also provides a method for creating reusable stylesheets~\cite{CustomizingMatplotlibStyle}, which allow the users to set default values for many of the aesthetic parameters of specific artists, e.g. "lines.linewidth : 3" and "xtick.labelsize : 16". These stylesheets are composable; for example, users can compose a stylesheet setting accessible colors with a stylesheet that adjusts text sizes and line widths for posters. 

\subsection{Color}
\begin{figure}

        \includegraphics[width=\linewidth, alt={Visual listing of the colors in the Okabe Ito, Petroff 6, 8, and 10, and Tableau 10, 20, 20b, and 20c named color sequences. All of the sequences have shades in the blue, orange, and purple families. The tableau sequences additionally have greens, yellows, and browns. Okabe-Ito has  a black, a yellow, and a green shade. The pretroff sequence contains two shades of gray.}]{color_sequences.pdf}
        \caption{Matplotlib provides the Okabe-Ito, four Tableau, and three Petroff accessible color sequences. Each sequence is designed so that each color is perceptually distinguishable from the other colors in the sequence.}
        \label{fig:color_cycle}
\end{figure}

Matplotlib's color sequences (palettes) are used by the plotting methods to automatically assign colors to visual elements. When plotting multiple line plots, for example, the first line takes the first color of the sequence, the second line takes the second color, the nth line the nth color, and the sequence cycles once the colors are exhausted. As shown in \autoref{fig:color_cycle}, Matplotlib's default color sequence is the tableau 10 color sequence, which is designed to be accessible to people with color vision deficiencies (CVD)~\cite{stoneHowWeDesigned}. Recently, Matplotlib has also added the Petroff color sequences~\cite{petroffAccessibleColorSequences2024}\footnote{added in versions 3.10.0 and 3.11.0}, which are designed with the aid of machine learning to balance accessibility constraints with aesthetic considerations, and the Okabe-Ito sequence\footnote{added in 3.11.0}, which aims to have reliable contrast on light and dark backgrounds and when converted to CMYK for printing~\cite{ichiharaColorUniversalDesignThe2008}. 

\begin{figure}
        \centering
        \includegraphics[width=\linewidth, alt={The berlin colormap goes dark blue to reddish pink, the managua colormap goes sky blue to orange, and the
        vanimo colormap goes bright green to bright pink. All three colormaps have a black center. These colormaps are displayed against a black background.}]{darkmap.pdf}
        \caption{The berlin, managua, and vanimo are dark-mode diverging colormaps,
        with minimum lightness at the center, and maximum lightness at the extremes.}
        \label{fig:dark_color_map}
\end{figure}

Matplotlib offers many  perceptually uniform sequential and diverging colormaps and the default colormap 'Viridis' is designed to be distinguishable for people with most forms of CVD~\cite{enthoughtBetterDefaultColormap2015}. Additionally, the recently added diverging dark mode colormaps~\cite{crameriScientificColourMaps2023} in \autoref{fig:dark_color_map}\footnote{added in version 3.10.0} to support dark mode, which is more accessible in some situations~\cite{atsaniRoleColorUser2025}. If these color sequences or maps do not suit the situation, Matplotlib also allows users to customize the color of every visual element in an image through the Artist interface. The colors can be specified in RGB/RGBA, HEX, grayscale, x11/CSS4, and a few library specific formats~\cite{SpecifyingColorsMatplotlib}. The colors module supports creating custom linear and categorical colormaps, the normalization pipeline, (composed of normalization and colormap methods) provides a variety of ways to encode numbers as colors, and the new colorizer module allows for even more customizability. Users can also create custom colormaps and norms and register external libraries of colormaps.

In addition to or in place of color, Matplotlib has rich support for using textures and shapes:
\begin{description}
\item[Markers: ] Matplotlib supports almost 40
named marker styles, markers created from Tex symbols, and custom markers created from
paths (arbitrary shapes)~\cite{MarkerReferenceMatplotlib}.
\item[Linestyles: ] Matplotlib provides 4 named line styles ('solid', 'dotted', 'dashed', 'dashdot') and allows users to configure the on/off sequence to create arbitrary patterns. 
\item[Hatches: ] Matplotlib also supports
10 hatch patterns that, as shown in \autoref{fig:hatch_patterns}, can be scaled and composed.
\end{description}

As shown in \autoref{fig:hatch_patterns}, markers, lines, and hatches can all be customized using color. Path effects~\cite{PathEffectsGuide} can be used to adjust the style of how lines, texts, and patches (shapes) are drawn. This can include adding effects such as shadows, outlines, strokes with a "hand drawn" aesthetic, and barbs as in \autoref{fig:hatch_patterns}. Additionally, Matplotlib supports generating custom fill patterns, as exemplified by third party libraries such as \cite{leeMpl_pe_pattern_monster011Documentation}. 

\section{Text}
As with color and texture, Matplotlib's fonts allow a very high level of customization so that users can choose the fonts, styles, weights, sizes, and colors best suited for their audience~\cite{FontsMatplotlibMatplotlib}. The default font \texttt{DejaVu sans}~\cite{DejaVuFonts} provides characters that are sans serif, unembellished, and distinguishable but does not guarantee consistent stroke width or symbol spacing. 
\begin{figure}[!h]

        plus the letter 'c' plus a diaeresis, producing a single glyph of all of them. An example of how text language affects rendering, showing the Unicode code point '\U00000431`, which is the Cyrillic small letter BE and the different renderings when the language is set to Serbian vs set to Russian.
        Last example is more mixed-language text "Also אַחַת שְׁתַּיִם שָׁלוֹשׁ in עִברִית".
        }]{libraqm.pdf}
        \caption{New support for complex text includes better support for using right-to-left languages, ligatures, diacritics, and localized variants of letters. }
        \label{fig:libraqm}
\end{figure}

Version 3.11 improves support for non-Latin alphabets; this can improve accessibility because graphs can be more easily created and understood when they incorporate conventions from the user's socio-cultural experiences~\cite{byrneAcquiredCodesMeaning2016}. This support is being added by extending text processing and rendering to use the \texttt{libraqm}~\cite{libraqm} and \texttt{HardBuzz}~\cite{WhatHarfBuzzHarfBuzz} libraries to handle complex text layout and rendering. As shown in \autoref{fig:libraqm}, this new text handling pipeline supports right-to-left and left-to-right texts, and parsing and placing letters, vowels, diacritics, ligatures, and variant character forms correctly~\cite{WhatHarfBuzzHarfBuzz,WhyNeedShaping}; therefore migrating to this new text processing and rendering stack allows Matplotlib to more easily support most of the writing systems covered by the Unicode standard.

In addition, Matplotlib also has a robust API for formatting ticks~\cite{MatplotlibtickerMatplotlib3103}. This means ticks can be styled with accessibility in mind - readable fonts, high contrast colors, font sizes and weights appropriate to the context. Additionally, users can incorporate local conventions, such as how numbers are formatted. 


\section{Alt text \& WAI-ARIA}
Alt text is a textual description of the visualization and WAI-ARIA is a framework for describing web content and applications\cite{initiativewaiWAIARIAOverview}; in Matplotlib, alt-text and ARIA support is backend dependent because screen readers interact with output, such as image files and application windows, and not Matplotlib internals. Backends are the software that manages the rendering of visual elements and handling of events~\cite{BackendsMatplotlib3110}, e.g. the artist defines the aesthetic properties and behavior of a line and the backend draws it to screen or file. Broadly, backends include static rendering engines such as Agg, Cairo, and PDF, interactive GUI frameworks such as QT, and GTK, and HTML/JavaScript widget frameworks such as ipympl. This separation of concerns at the architecture layer makes it technically feasible to develop accessibility API drawing from the Artist and customized to each backend; but, efforts such as adding a wai-aria property~\cite{ImproveAccessibilityFigures,AddWaiariaProperty} stall out for many years because the developers do not know what information about the artist should be encoded and therefore which architecture and implementation decisions to move forward with.



\subsection{Static Backends}

Matplotlib can write arbitrary metadata (including EXIF tags) to the static image files, (e.g. png, jpeg, pdf, gif) it can output, which developers can use to build downstream tools targeted to specific backends, such as MatplotAlt~\cite{nylundMatplotAltPythonLibrary2025} for computational notebooks, or custom accessibility aware backends such as py-maidr~\cite{PymaidrAccessibleData}. Matplotlib could encourage this adaptor like approach, similar to Olli~\cite{blancoOlliExtensibleVisualization}, but it raises questions on which defaults and guardrails, as described in the Bokeh Accessibility Audit~\cite{elavskyBokehAccessibilityAudit}, Matplotlib should implement internally vs delegate to downstream libraries implemented by developers who have expertise in accessibility. For example, some formats (e.g. vector) have the ability to attach information to individual parts of a figure, whereas raster formats can only attach such alt text to the figure as a whole. Matplotlib can attach this information at the figure level and the artist level, but would it be more useful for Matplotlib to pass the tree to downstream tools or combine the information depending on backend or a different criteria? For example by potentially implementing something similar to the semantic layers in~\cite{plotnine}, specifically targeted to screen readers, as recommended by WebAIM~\cite{WebAIMCSSAction}. Should Matplotlib auto populate fields using artist information or raise a warning that users did not add alt text or neither? How how much granularity is useful to provide- e.g. parent artists know about their children, does the tool need both to report, the relationship between the two, etc., --- and in what format? 


\subsection{Interactive Applications}
Matplotlib's independent widget system is implemented by rendering most of the Matplotlib interactive backends as static bitmaps with an event system layer on top. The accessibility trade off is that Matplotlib usually cannot provide individual GUI elements for screen readers to query, but developers are not limited to the widgets provided by a specific framework and instead they can build basically any interaction that the event system~\cite{InteractiveFiguresAsynchronous} supports. Additionally, developers who need accessible GUIs have the option of using the GUI widgets, which provide whatever accessibility is built into the framework (e.g. QT), rather than the Matplotlib widgets. This leans into the option driven design philosophy of giving users and developers the tools to create interfaces tailored to access needs rather than trying to assume those needs. 

Like the static backends, the accessibility of GUI and widget framework backends can be improved on a per backend basis. For example, there's ongoing and planned work to improve various aspects of macOS, namely adding proper labels to the artist, adding more dark mode support~\cite{BugMacOSBackenda} and reducing flickers when resizing~\cite{BugMacOSBackend}. An added bonus of the semi-independent backends architecture is that development in Matplotlib, like most open source projects, is heavily dependent on who is able to contribute free labor, and it is far more likely that a contributor feels capable of improving the backend that they are most familiar with (such as macOS) than all the backends. While the improvements may be piecemeal, they could provide users with an option where there currently may not be one.


\section{Discussion}
There has been ongoing work to implement a new data container~\cite{ProofConceptData} in Matplotlib to provide a uniform interface to the data. This work is motivated by Matplotlib having an inconsistent internal data access model, which makes it difficult to change the data in a uniform manner across all the artists and plotting methods. For example the line artist and image artist have different API methods for accessing data, and transforms, scales, and unit conversions are not always applied consistently across plotting methods. While accessibility is not the main goal, a positive side effect of unifying the model of internal state is that it would provide a consistent interface for accessibility tools to query for information about the state of the visualization. 

A secondary goal of the data container work is reworking the visual encoding and assembly work handled by the artist into a more modular pipeline that is also more explicit about how visual elements correspond to distinct data elements. Similar to the uniform data interface, the goal is to be more consistent in how changes are applied to the data. Maintaining that correspondence would allow the artist to retain more information about the visual elements and this information could be passed along to screen readers in a reliable way. The new transformation pipeline is also intended to keep track of the underlying structure of the data, providing a framework for developers to safely stack composable encoders, akin to the Encodable library~\cite{wongsuphasawatEncodableConfigurableGrammar2020}. For example, a method for converting an arbitrary colormap to a CVD safe one can be verified to be structure compatible if it knows the structure of the data it is converting. The same is true for the full visualization, for example a structure aware pie chart can more reliably replace inaccessible elements with accessible elements, such as replacing colors with hatches. To implement structure awareness, work needs to be done towards standardizing the properties of the internal visual parameters of Matplotlib. Like standardizing the data interface, standardizing the parameters would improve accessibility by creating a consistent standard for developers writing new functionality, such as libraries for accessible stylesheets or auto generating alt text, to hook into. 


\section{Conclusion}
Matplotlib's option driven design provides accessible defaults and many ways to customize the graphic to make the various elements more accessible. There are architectural challenges that make it difficult to make interactive visualizations more accessible, but the artist tree stores information that could potentially be exposed to accessibility tools, for example to populate alt-text and compensate for the inability to introspect GUI elements. In keeping with options driven ethos, it would be inappropriate for Matplotlib to provide AI generated content as that would limit the downstream developers options. Instead, Matplotlib maintainers (and contributors) can implement an interface for downstream developers, if given some guidance on what sort of interface would be useful.
